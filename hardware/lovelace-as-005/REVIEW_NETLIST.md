## 2. 핀은 맞지만 확인이 필요한 것

1. **[Minor, 실측 확인 — R15 5.1k 유지, 절차는 [BRINGUP.md](BRINGUP.md) 7절] eFuse 전류 제한 여유는 약 40%입니다.** ESP32-WROVER-E 데이터시트 표 16에서 모듈 피크는 350mA입니다(802.11b 1Mbps, 19.5dBm, 송신 100% 듀티). 버크 효율을 85%로 잡으면 4.75V 입력에서 0.29A이고, DAC LDO 31mA와 CH340N·LED를 더하면 약 0.33A입니다. ILIM 최소값 0.56A보다 0.23A 낮습니다. 시뮬레이션(4절)에서는 3.3V 쪽 피크가 0.6A(5V 입력)·0.5A(4.4V 입력)까지 버텼습니다. 데이터시트 피크의 1.4–1.6배입니다. 처음 적은 0.45A는 데이터시트의 "외부 전원은 0.5A 이상 공급" 권장값을 부하로 잘못 쓴 계산이었습니다. 그 값은 공급 능력 기준이고 실제 부하가 아닙니다. Bluetooth와 Wi-Fi는 시분할이라 전류가 더해지지 않습니다. TPS259470A는 한계를 넘으면 끊지 않고 전류를 제한합니다. 그래도 버크는 입력이 약 3.5V 이상이면 3.3V를 유지하므로, 실제 문제는 ESP32 리셋으로만 나타납니다. 첫 보드에서는 웹 UI의 리셋 원인과 업타임으로 이를 확인합니다. 리셋이 생기면 R15를 4.3k로 바꿉니다(0.78A, 0.66–0.89A). 다만 Rd만 있는 USB-C 기본 전원 상한(500/900mA)에 가까워집니다.
2. **[Minor] 인덕터 포화 전류 2.1A < TPS62162 전류 제한 최대 2.45A.** Murata DFE201612P-2R2M 표의 최대값은 인덕턴스 30% 감소 기준 2.1A(typ 2.3A), 온도 상승 40°C 기준 1.5A(typ 1.8A)입니다(이전 판은 둘을 뒤바꿔 적었습니다). 정상 부하(피크 약 0.6A)에서는 문제가 없습니다. 3.3V 쇼트나 과부하 때만 인덕터가 포화합니다.
3. **[Minor] 상태 LED가 어두울 수 있습니다.** `plan_pcb.py` 주석은 Vf를 약 2.9V로 적었지만, JLC 데이터의 KT-0603G는 5mA에서 Vf 3.1V(에메랄드 그린)입니다. 3.3V와 220Ω이면 약 1–2mA라 어둡게 켜집니다. 밝기가 중요하면 R18을 100Ω으로 바꿉니다.
4. **[Minor] C25 감액.** 6.3V 폴리머 탄탈은 10% 감액 기준으로 5.67V까지 권장됩니다. 평소 4.7V에서는 문제없고, 입력이 OVLO 한계 6.0V일 때만 약 5.7V가 됩니다.

## 4. 전원 경로 시뮬레이션 (ngspice)

[`sim/power_path.py`](sim/power_path.py)는 USB 전원과 케이블 → eFuse → +5V → 버크 → ESP32, 그리고 +5V → D5 → C25 → LDO → DAC 경로를 데이터시트 수치로 만든 동작 모델입니다. ngspice 47로 돌렸고 결과는 `reports/sim.json`에 있습니다.

모델에 넣은 것은 다음과 같습니다.
- eFuse: UVLO 4.26V 켜짐 / 3.87V 꺼짐, OVLO 5.80V, dV/dt 0.2V/ms(10nF), RON 30mΩ, ILIM 즉시 동작, 역전류 차단.
- 버크: 효율 80%(보수적). LDO 강하 20mV.
- ESP32 부하: EN RC(10k/1µF) 뒤에 켜지고, 1ms 켜짐 / 1ms 꺼짐 펄스. 기본 115mA에 CH340N·LED 포함.
- 커패시터: 동작 전압에서의 DC 바이어스 감소 반영. 모듈 내부 커패시터는 빼서 보수적으로 잡았습니다.

넣지 않은 것: 실제 레이아웃 기생 성분, 버크 제어 루프 응답, eFuse 폴드백, ESP32의 실제 전류 파형.

**기동** (꽂는 순간, 부팅 직후 RF 보정을 최대 송신으로 가정)

| 입력 | ILIM | +5V 90% | 3V3 3.2V | ESP32 켜짐 | eFuse 최대 | 전류 제한 |
|---|---|---|---|---|---|---|
| 5.0V / 0.1Ω | 0.556A | 22.5ms | 16.3ms | 23.9ms | 383mA | 0ms |
| 4.4V / 0.3Ω | 0.556A | 19.8ms | 16.3ms | 23.9ms | 383mA | 0ms |

커패시터 충전 돌입 전류는 약 50mA입니다(0.2V/ms × 약 240µF). 기동 중 전류 제한에 걸리지 않습니다. 처음 모델에는 UVLO 히스테리시스가 없어서, 4.4V 입력에서 케이블 강하로 eFuse가 꺼졌다 켜지기를 반복하는 결과가 나왔습니다. 데이터시트의 꺼짐 기준(1.09V)을 넣자 사라졌으므로 회로 문제는 아닙니다. 다만 UVLO 켜짐 기준이 최대 4.39V이므로, 4.4V 근처 전원에서는 아예 켜지지 않는 보드가 있을 수 있습니다. USB 규격 최저값은 4.75V입니다.

**펄스 부하** (3.3V 쪽 피크 전류를 올려 가며 측정, 60–120ms 구간)

| 입력 | ILIM | 0.37A (데이터시트) | 0.5A | 0.6A | 0.7A |
|---|---|---|---|---|---|
| 5.0V | 0.556A | +5V 4.94V, 제한 0 | 4.92V, 0 | 4.90V, 0.24ms | **붕괴** (+5V 3.0V, 3V3 2.2V) |
| 5.0V | 0.654A | 4.94V, 0 | 4.92V, 0 | 4.90V, 0 | 4.88V, 0.22ms |
| 4.75V | 0.556A | 4.67V, 0 | 4.64V, 0 | 4.61V, 7ms | **붕괴** |
| 4.4V | 0.556A | 4.27V, 0 | 4.23V, 0 | **붕괴** | **붕괴** |
| 4.4V | 0.654A | 4.27V, 0 | 4.23V, 0 | 4.20V, 0 | **붕괴** |

붕괴는 버크가 일정한 전력을 끌기 때문에 생깁니다. 전류 제한에 걸린 상태가 길어지면 +5V가 떨어지고, 버크는 같은 전력을 얻으려고 전류를 더 끕니다. 그러면 +5V가 다시 떨어지는 악순환이 됩니다. 결국 3V3가 브라운아웃 기준 2.43V 아래로 내려가 ESP32가 리셋됩니다. 따라서 여유가 부족하면 나타나는 증상은 리셋이고, BRINGUP.md 7절의 리셋 원인 확인으로 잡힙니다. 데이터시트 피크(0.37A)에서는 모든 조건에서 전류 제한에 걸리지 않았습니다.

**홀드업** (재생 중 USB 분리)

| 입력 | ESP32 부하 | ESP32 꺼짐(3V3 < 2.43V) | DAC 꺼짐(3V3A < 3.2V) | 여유 | 필요 |
|---|---|---|---|---|---|
| 5.0V | 80mA | 0.6ms | 10.8ms | 10.2ms | 3.6ms |
| 5.0V | 250mA | 0.2ms | 10.7ms | 10.5ms | 3.6ms |
| 4.4V | 80mA | 0.5ms | 6.4ms | 5.9ms | 3.6ms |
| 4.4V | 250mA | 0.2ms | 6.0ms | 5.9ms | 3.6ms |

ESP32는 분리 후 1ms 안에 꺼져 I2S 클럭이 멈춥니다. DAC는 그 뒤로도 5.9ms 이상 전원을 유지해 3.6ms짜리 클럭 정지 소프트 뮤트를 마칩니다. README의 계산(9.6ms / 5.3ms)과 같은 방향이고, 모든 조건에서 여유가 있습니다.

**다시 돌리기:** `python3 sim/power_path.py`(ngspice 필요, `brew install ngspice`). 기준을 하나라도 못 맞추면 종료 코드 1을 냅니다. 기준은 데이터시트 피크에서 전류 제한이 걸리지 않을 것, 3V3 3.2V 이상, 홀드업 여유 3.6ms 이상입니다.
